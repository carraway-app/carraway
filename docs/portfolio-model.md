# Portfolio model: investments, instruments, commitments, tranches and transactions

Design and implementation notes from 23 November 2026. The phase notes capture behaviour at the time of implementation and retain the identifiers in use then. See the [API glossary](api-glossary.md) for public API names.

## Purpose

A company's portfolio view follows the order in which an investment takes shape.

1. **Financing round** at the company, with positions from internal funds and third-party investors.
2. **Instrument** per fund: equity (shares), silent participation, loan, convertible loan, venture debt or shareholder loan. Optionally link a round and a share class. A company can have several instruments per fund, including several of the same type.
3. **Commitment** per instrument, split into **tranches** (amount, scheduled date and optional condition).
4. **Ledger transactions.** Disbursements fill tranches. Further transactions record proceeds, repayments, interest, interest payments and dividends.

For third-party investors, commitment equals the round position's amount. Third-party payments are optional and informational.

## Data model

### Investment (fund × company)

- Unique by `(fonds_id, organisation_id)`. Previously unique by fund, company and instrument. The existing data had no duplicate fund and company pairs, so it could transition without merging.
- Holds company position status, initial investment, currency, custom fields, valuations, documents and company net income.
- `beteiligung.instrument` and `instrument_felder` remain for Excel, the public API and import. They mirror the **main instrument** (first active, or most recently created if none is active). Removal waits until all readers have switched.

### Instrument (new table `instrument`)

| Column | Meaning |
|---|---|
| `beteiligung_id` | Required |
| `art` | Enum `instrument`, extended with `venture_debt`, `gesellschafterdarlehen`, `safe`, `optionsschein` |
| `bezeichnung` | E.g. “Seed shares”, “Convertible loan 2024”. Defaults from type and round. |
| `runde_id`, `anteilsklasse_id` | Optional |
| `status` | `aktiv`, `gewandelt`, `getilgt`, `verkauft`, `abgeschrieben` |
| `felder` | Custom fields for `instrument` (copied from `beteiligung.instrument_felder`) |

Loan-like instruments have terms, interest and repayments: `darlehen`, `wandeldarlehen`, `stille_beteiligung`, `venture_debt`, `gesellschafterdarlehen`.

The instrument takes over `darlehen_kondition`, tranches (formerly `meilenstein`), `zinslauf_position`, `zinsperiode_gebucht` (unique by instrument and period end), `wandlung` (source and target), `verkauf` and `forderung` where they concern an instrument. The `instrument_id` column is backfilled from the investment. Internal fund positions in rounds reference their instrument (`rundenposition.instrument_id`, fund positions only).

### Commitment and tranches

- A **commitment** remains a transaction of type `zusage`, with immutability, reversal, knowledge date and DATEV source `zusage` preserved. It now has `instrument_id`. An instrument's commitment is the sum of its `zusage` transactions.
- A **tranche** (table `tranche`, renamed and extended from `meilenstein`) has `instrument_id`, `nummer`, `bezeichnung`, `betrag`, `geplant_am` (formerly `frist`), `bedingung`, `erfuellt_am` and `nachweis`. It schedules when a portion of the commitment is paid and posts no money.
- Sum of tranches ≤ commitment (`tranches_exceed_commitment`). If the commitment would otherwise be insufficient, “Add tranche” creates the tranche and its `zusage` transaction in one step.
- A **disbursement** requires an instrument and can reference a tranche (`vorgang.tranche_id`, formerly `meilenstein_id`). A tranche is committed, partially paid or paid (sum of disbursements ≥ amount). Its condition, if present, is pending or fulfilled. Disbursement to a conditional tranche requires a fulfilled condition.
- Disbursements per instrument must stay within that instrument's commitment (`disbursement_exceeds_commitment`).

### Ledger transactions

`vorgang.instrument_id` is required (backfilled from the investment for existing rows).

| Group | Type | New? | Meaning |
|---|---|---|---|
| Investing | `zusage` | | Commitment, usually through “Add tranche” |
| | `auszahlung` | | Disbursement to the company, on an instrument and tranche |
| Income | `zinszahlung` | Yes | Interest received in cash |
| | `dividende` | Yes | Profit distribution on equity |
| | `zins` | | Interest posting from the run (a receivable), marked `kapitalisiert` when added to principal |
| Proceeds | `tilgung` | | Repayment of debt principal |
| | `rueckfluss` | | Sale or exit proceeds |
| Legacy | `wertberichtigung` | | No longer offered in transaction entry. See below. |

Conversion, sale, insolvency and seller financing remain separate instrument workflows. Conversion moves from its source instrument to a new equity instrument within the same investment, replacing the earlier second-investment approach.

New enum values are added in a separate migration and used in a later migration because PostgreSQL cannot use a newly added enum value in the same transaction.

### Impairment

An accounting impairment belongs with valuations. The UI offers “Impairment (accounting)” in **Valuations** and removes it from “Record transaction”. Underneath it remains a `wertberichtigung` transaction on the instrument to preserve carrying amount, DATEV export, import and existing records. It still appears with a label in the transaction list.

## Interest

- Terms and calculation rules stay the same, now per instrument.
- An **interest posting** (`zins`) comes from an approved interest run per fund and as-of date, at period end. It records a receivable.
- An **interest payment** (`zinszahlung`) records incoming cash by manual entry or import. It can reference the settled interest posting.
- **Outstanding interest** = booked interest excluding capitalised and converted interest − interest payments. Capitalised interest increases principal and carrying amount and is never outstanding.
- **Converted interest.** With `zinsen_wandeln = true`, the conversion's interest posting (keys `darlehen_zins_*` in `wandlung.vorgaenge`) converts into shares with principal. Conversion settles it without a cash interest payment. The period status is “Converted”, and a separate “Converted” metric appears per instrument and in totals, with tile and column only when nonzero. With `zinsen_wandeln = false`, conversion still posts `zins`, which remains outstanding until cash is recorded as an interest payment. This applies to investment and fund views and to `offeneZinsen` in instrument data, which adds `gewandelteZinsen`.
- **Accrued interest** = unposted periods plus the current period up to the as-of date, using the existing accrual calculation.
- **Existing data.** Migration creates an interest payment with the same date and amount for every posted, non-capitalised and unreversed interest posting (“migrated from existing data”). This preserves journal and liquidity figures.

### Views

- **Investment → Capital → Interest** (only with a loan-like instrument) shows terms, accrued, booked, capitalised, paid, outstanding, next due date and periods per instrument at the page's as-of date. Action “Record interest payment”.
- **Fund → Interest** in the fund shell shows the same values per instrument for the whole fund, with totals, an as-of date and links to the investment and interest runs.
- Fund administration → Interest accruals remains for accounting.
- API: `GET /beteiligungen/:id/zinsen?stichtag=&stand=`, `GET /fonds/:id/zinsen?stichtag=&stand=`.

## Metrics

- **Invested** = disbursements.
- **Proceeds** = sale proceeds + repayments + interest payments + dividends.
- **Conversion postings are non-cash.** Loan repayment by conversion to shares and the target's commitment and contribution are excluded from invested, proceeds, multiple, DPI, TVPI and IRR. This applies to investment and fund overview, portfolio and exit lists, currency views, reports, Excel, regulatory reporting, accounting reconciliation, scenario flows and reserves. Only the cash residual (second loan repayment) remains proceeds. Converted interest is an interest posting (receivable) and never counts. Position and carrying amount are unchanged. The repayment takes the loan to zero and the contribution is the target's acquisition cost (carrying amount, outstanding principal, unfunded commitment and “Paid out” by instrument). The entries are recognised through `wandlung.vorgaenge` (keys `ziel_zusage_*`, `ziel_auszahlung_*`, `darlehen_tilgung_*`, with the last repayment the cash residual if positive, and `darlehen_erlass_*` for contractually waived principal). Repayment of remaining principal (`darlehen_rueckzahlung_*`) and the interest payment (`darlehen_zinszahlung_*`) are cash and remain proceeds. A reversal is treated like its original (`instrumente/geldfluss.ts`, SQL condition `geldlos`, `ladeGeldloseIds`). Investment transaction rows expose `ohneGeldfluss`.
- **IRR** and **multiple** use these cash flows plus valuation. Interest postings (`zins`) are excluded. Only interest actually paid counts.
- **Journal and liquidity.** Cash moves with `zinszahlung` and `dividende`. An interest posting no longer counts as cash received.
- **Carrying amount** stays the same: invested + capitalised interest − repayments − impairment − disposals.
- Python references (`packages/rechenkern/referenz/`) follow these rules.

### Fund NAV as of a date

Portfolio value sums the latest effective approved investment valuations. A partial sale leaves the residual valuation in place. A full exit uses effective status at the as-of and knowledge dates.

**Fund NAV = portfolio value + cash at bank + other assets − liabilities and provisions.** Use the applied trial balance for exactly that period end. When replaced, the previous trial balance applies until the replacement is applied. Account rules at application assign each row's balance sheet group. Migration 0077 uses rules effective at period end from the account plan present during migration for legacy trial balances.

- `aktiva.finanzanlagen` contains the portfolio's carrying amounts. Approved valuations replace them in NAV.
- `aktiva.liquide` gives cash at bank. Other assets include outstanding purchase price receivables. Incoming payment reduces receivables and increases cash at bank. The sales register explains the outstanding amount per investment. The fund takes the purchase price from the balance sheet exactly once.
- Liabilities outside `passiva.eigenkapital` reduce fund NAV. Debit balances enter positively, credit balances negatively.
- Without the trial balance, an explicit bank row or a mapping for any nonzero account balance, fund NAV, LP NAV share, TVPI, RVPI and IRR are unavailable. An explicit zero bank balance is valid. Portfolio value and DPI remain available.
- The control report compares fund NAV to equity including earnings on the liabilities side, to the cent. Carrying amounts and approved valuations can differ. The report shows the difference for explanation.

In demo trial balances at 30 September 2026, account 0120 shows the difference between posted financial assets and approved quarterly valuations. The contra posting goes through income or impairment. This makes equity match fund NAV. The separate carrying amount reconciliation still shows the example difference of €1,000.00 for the first fund.

Fund overview and reports display aggregated balance sheet amounts. The NAV provenance dialog can open the underlying valuation, its approval and visible document pages. With finance read access on the fund, it can also open contributing accounts from the applied trial balance. Individual amounts have the sign of their NAV contribution and use fund currency. Links carry the as-of and knowledge dates. A stored quarter-end view uses the saved calculation's cut-off. The fund overview comparison currency converts the full NAV at the as-of date rate.

## Workflows

- **Close a round.** For each internal fund position, find or create its investment, create an instrument (type from the position, equity by default, round and share class set) and post a commitment equal to the position (now on by default) with one tranche and optional initial disbursements.
- **Capture a contract (AI extraction, managed hosting).** An investment agreement creates a draft round as before. Confirming a loan agreement creates an instrument (type from the agreement), commitment, tranches and terms. It creates the investment if one does not exist for fund and company.
- **Record transactions** by investing, income and proceeds. Disbursement requires an instrument and offers open tranches. Interest payment needs a loan-like instrument. Impairment appears under valuations. The UI also offers “Add instrument” and “Add tranche”.

- Capital: Financing rounds, Instruments, Transactions, Interest, Cap table and Exit scenario.
- Value, Files and Master data as before.
- Company: Metrics and Boards.

- Creating, editing and deleting mandate master data logs a change under the investment's fund. Viewing requires viewer and editing requires editor on that fund in portfolio.
- API: `GET`/`POST /beteiligungen/{id}/mandate`, `PATCH`/`DELETE /beteiligungen/{id}/mandate/{mandatId}`, `GET /fonds/{id}/mandate?stichtag=` (all mandates on fund investments, or active on the supplied date). ## Implementation phases

Each phase passes type checking, lint, tests including `api` and `db` against `carraway_test`, build and bundle budget.

1. **Database.** Enum values, `instrument`, `meilenstein` → `tranche`, new columns, backfill, cash interest payments and seed. Old columns remain.
2. **API and calculation engine, core.** Instruments, tranches, transactions per instrument, closing a round, conversion, sale, per-instrument interest runs and validation.
3. **API and calculation engine, reporting.** Metrics, journal, liquidity, interest views, AI confirmation, import, reports, Excel and the public API (retain old fields and add `instrumente)), plus Python references.
4. **UI.** Navigation, instruments and interest sections, Fund → Interest, dialogs, valuations with impairment and closing a round.

### Phase 1 status: transition

- The database enum `instrument` becomes `instrument_art` because the new table uses `instrument`. Column names remain `art` and `beteiligung.instrument`.
- Uniqueness by `(fonds_id, organisation_id)` waits until phase 2. Until then conversion creates a second (equity) investment for the same fund and company, and the fund/company/instrument index remains.
- `darlehen_kondition` also remains unique per investment and date until calculations use instruments. `zinsperiode_gebucht.instrument_id` is required and unique by instrument and period end.
- Each migration runs in its own transaction in `scripts/migrate.ts` so an enum value added by `ADD VALUE` is available in the next migration.
- In phase 1 each transaction, term and tranche uses the investment's **main instrument** (`apps/api/src/instrumente/hauptinstrument.ts`). API paths and fields (`meilensteine`, `meilensteinId`, `frist`) remain and responses add the new fields. Interest payments and dividends count in analyses from phase 3.
- Migration `0062` creates “Tranche 1” for migrated commitments without a tranche, using the effective commitment and the value date of the first unreversed commitment. It assigns the instrument's disbursements without a tranche, including reversals. Instruments with tranches stay as-is. If disbursements exceed commitment, the migration skips and reports the instrument. The demo seed already creates tranches.

### Phase 2 status: API by instrument

New routes (viewer to read, editor to write, as with other investment writes): `GET` and `POST /beteiligungen/:id/instrumente`, `GET` and `PATCH /instrumente/:id`, `GET` and `POST /instrumente/:id/tranchen`, `PATCH /tranchen/:id`, `POST /tranchen/:id/erfuellt`. Legacy paths and fields (`/beteiligungen/:id/meilensteine`, `/meilensteine/:id/erfuellt`, `meilensteinId`, `frist`) use the same functions and retain their names and audit log identifiers. New codes have German and English UI text: `instrument_not_found`, `instrument_wrong_investment`, `instrument_not_active`, `instrument_type_locked`, `tranches_exceed_commitment`, `tranche_wrong_instrument`, `interest_payment_reference_invalid`.

Migration `0059` merges existing duplicate fund/company pairs into the oldest investment and moves every foreign key on `beteiligung`. A terminated loan valuation at a prior conversion's cut-off becomes `ersetzt`. Any other conflict stops the migration with an explicit message. Uniqueness becomes `(fonds_id, organisation_id)` for investments, `(instrument_id, gueltig_ab)` for terms and source instrument for conversion. `0060` adds `verkauf.verkaeuferdarlehen_instrument_id`, clears `verkauf.instrument_id` for legacy rows and requires `wandlung.quell_instrument_id`. The demo portfolio (`schreibeDemoPortfolio`) keeps one investment per fund and company.

- **Transaction instrument.** Use `instrumentId` (and `trancheId`, formerly `meilensteinId`) in the body. With several instruments it is required (400 `instrument_erforderlich`), or the tranche supplies its instrument. With one instrument it defaults to that one. Impairment follows the same rule. Terms (`instrumentId`) and conversion (`instrumentId`, defaults to a sole active convertible loan) resolve similarly.
- **Validation by instrument.** Commitment, principal history and reversal of impairment are per instrument. Carrying amount cannot be negative per investment. A disbursement to a tranche with a condition requires fulfilment. A tranche without a condition no longer needs fulfilment, unlike the old milestones. Only the new path checks total tranches against commitment.
- **Conversion.** The source becomes `gewandelt` and the target is a new equity instrument in the same investment (“<round> shares”, round set). The investment stays active. There is one valuation per investment at cut-off: previous value minus terminated loan carrying amount (floored at zero) plus converted amount. A second conversion of the same instrument returns `already_converted`.
- **Contractual adjustments.** Conversion and preview optionally accept `gewandeltesDarlehen` and `gewandelteZinsen` (at most two decimal places, from zero to the calculated balance at cut-off, interest only with `zinsenWandeln`; otherwise 400 with field finding `ueber_ausstehend`, `zinsen_nicht_gewandelt`, `nichts_gewandelt` or `unter_spitzenbetrag`) plus `darlehenRest` and `zinsenRest` (`zurueckgezahlt` by default or `erlassen`). Omission uses calculated balances. Conversion amount = converted principal + converted interest. Shares = conversion amount ÷ conversion price, rounded down. The rounding residual remains a cash repayment of the converted loan. Post the unconverted remainder at cut-off as new transactions, preserving ledger immutability. Repaid principal is a cash repayment (`darlehen_rueckzahlung_*`) and waived principal is a non-cash repayment (`darlehen_erlass_*`, included in `geldlos`, excluded from proceeds). Paid interest posts the remaining interest (`darlehen_zinsrest_*`, unconverted) plus its settling interest payment (`darlehen_zinszahlung_*`, proceeds). Waived interest is never booked as a receivable. The calculation engine returns `darlehenGewandelt`, `zinsenGewandelt`, `darlehenRest` and `zinsenRest`. The API adds `restbehandlung` (`darlehen`, `zinsen`: treatment or `null` when no remainder) to `wandlung.ergebnis`. No migration is needed. Estimates for open conversions retain calculated balances. The Conversion dialog has an optional contractual adjustments group with converted principal and interest and treatment of each remainder. Preview shows unconverted principal and interest. Open conversions show a notice.
- **Close a round.** Each internal fund position creates investment, instrument (`art`, `bezeichnung` per entry), commitment and a tranche. If `fondsBuchungen` has no entry, commitment defaults on where the user has editor rights. `zusage: false` skips commitment and tranche. Reclosing after reopening retains instrument, commitment and tranche. A round and its position cannot be deleted once the position has an instrument.
- **Sale.** Omit `instrumentId` to sell the whole investment. A full sale marks all active instruments `verkauft` and leaves `verkauf.instrument_id` empty. With `instrumentId`, sell only that instrument. The investment becomes `exit` when no instruments remain active. Reversal restores only instruments not covered by another unreversed full sale. Insolvency marks active instruments `abgeschrieben` and applies impairment per instrument.
- **Seller financing.** The debtor is usually the buyer. If its fund has no position there, create an investment with a loan instrument. Otherwise add the instrument to the existing investment (`investment_exists` if a loan already exists). If omitted, the sold company is the debtor. The loan is then on that same investment, which stays active. The sale-date valuation includes the remaining stake and loan.
- **Interest runs** calculate and post per loan-like instrument (`zinslauf_position.instrument_id`, `abgedeckt[].instrumentId`). Only active instruments of active investments participate.
- **Uniqueness.** Deal transfer and import return `investment_exists` if the fund already holds the company. Add instruments via `POST /beteiligungen/:id/instrumente`. Two organisations held by the same fund cannot be merged.

### Phase 3 status: API and reporting

### Capital calls and incoming payments

A call fixes each investor's cent amount using the allocation effective at the call date. Its due date can be later and defaults to the call date. Each incoming payment belongs to a call and investor and has its own value date. Partial payments reduce the outstanding amount from that date. Any remainder is overdue starting the day after the due date. Unfunded subscription commitment remains commitment minus calls.

In demo data, LP payments enter the bank balance on their value dates. At quarter end, outstanding calls appear under other receivables (account 1400).

### Management fees and fund expenses

Expense postings (`fonds_kosten`) record management fees and other fund expenses. No money moves between fund and investors. The posting reduces capital accounts. Enter the amount or calculate it from the annual rate: sum of commitments for investors with a weight at period start × rate × days (both endpoints inclusive) / 365, rounded to cents. Allocate by the basis at value date (largest remainder, as for calls) or by a custom split that adds to the amount exactly. Shares are fixed in `fonds_kosten_anteil` and later closings do not reallocate them. Reversal negates the amount and its shares.

Fund NAV still comes from the trial balance, which already reflects paid costs in cash and unpaid costs in liabilities. Expense postings leave NAV and fund metrics unchanged. For each investor:

- NAV share = NAV allocated by weight + equalisation. Each entry's equalisation is the amount jointly borne by weighted investors, allocated by weight, minus the investor's actual share. It is zero for strictly pro rata expenses. NAV shares still add up to NAV.
- Roll-forward: paid-in capital − distributions − management fees − fund expenses + performance and other earnings = NAV share.
- Investor net IRR: XIRR of contributions and distributions, with NAV share as terminal value on the as-of date.

Liquidity reconciliation subtracts posted expenses from cash flow at value date. Unposted expenses still appear as differences against cash at bank. The demo posts the trial balance's management costs (account 6300) as three quarters of management fees and one fund expense, allocated pro rata.

Capital position includes calls, payments and their reversing entries through the as-of and knowledge dates. A payment reversal references the original and gives a reason. At a prior as-of date, the original still counts. From the reversal value date, both drop out of effective cash flow. Reverse a call's payments before reversing the call.

In Capital, “Called” and “Paid in” open their components in fund currency. The call shows posted shares per investor. The payment shows value date and recorded voucher reference. Original and reversal reference each other and cancel in totals. The source links to the call, investor notices approved at the selected knowledge date and voucher files available then.

For legacy postings, the value date used in notices serves as due date. An approved notice supports the called amount. Receipt of cash requires a separate payment voucher. Old outstanding amounts appear as unconfirmed. Record evidence at its actual value date. An optional voucher reference can identify a bank statement line. Approved reports and notices retain their file and checksum. New calculations use evidenced receipts, including for earlier as-of dates.

The internal API accepts a call through `POST /fonds/:id/buchungen` with `typ: "fondsbewegung"`, `art: "abruf"`, `betrag`, `valuta` and optional `faelligAm`. Amounts are decimal strings in fund currency.

| Route | Contents |
|---|---|
| `GET /fonds/:id/bewegungen/kapitalstand` | `stichtag`, optional timestamp `stand`. Returns `quellenstand`, `fonds` and `konten` with called, paid-in, outstanding, overdue and unconfirmed amounts. |
| `GET /fonds/:id/bewegungen/herkunft` | Components for `stichtag` and `stand`. `bewegungId` also returns the posted call and approved evidence. |
| `GET /fonds/:id/bewegungen/mitteilungen/:mitteilungId/datei` | Approved notice PDF at the same as-of and knowledge dates. |
| `GET /fondsbewegungen/:id/zahlungen` | Call components and payment history. Optional `stichtag` and `stand`. |

| `POST /fondsbewegungen/:id/zahlungen/storno` | `zahlungId`, `valuta` and `grund`. Returns the reversal with `storniertZahlungId`. |

`ladeKapitalstand(tx, fondsId, stichtag, stand?)` returns fund and LP totals, individual called amounts, due dates, payments and reversal references. DPI, TVPI and RVPI use paid-in capital as their base. XIRR uses the value dates of effective contributions and distributions and the fund NAV at the as-of date.

**Metrics.** Proceeds = sale proceeds + repayments + interest payments + dividends (`RUECKFLUSS_ARTEN`, `istRueckfluss` in the calculation engine). This applies to investments (calculation steps, multiple, IRR), fund overview rows, currency views, reports and their checksums, scenario bases (gross flows), and the proceeds balance in regulatory reports. Interest postings (`zins`) never count and capitalised interest creates no cash flow. Fund TVPI, DPI, RVPI and fund IRR still use fund movements (calls and distributions) and NAV. Received interest and dividends reach them through fund distributions. The calculation label is “Cumulative proceeds (including interest paid and dividends)” with English in the web app and reports. Python reference `referenz_rueckfluesse.py` calculates proceeds, multiple and IRR with a reversal pair, interest posting, interest payment and dividend. `kennzahlen.test.ts` compares against it.

**Journal and liquidity.** `zinszahlung` and `dividende` are cash inflows. Interest posting has no cash effect. Liquidity reconciliation shows “Interest paid” and “Dividends” in place of “Interest (non-capitalised)”. Journal types `zinszahlung` and `dividende` have filters and labels.

**DATEV and posting rules.** Migration `0061` adds sources `zinszahlung` and `dividende` using only `ADD VALUE`. Demo defaults: interest posting 1400 (receivables) to 4200 (interest income), interest payment bank 1200 to 1400 and dividend bank 1200 to 4900. Funds configure their own rules (`PUT /fonds/:id/buchungsregeln/:quelle`). A missing rule produces `posting_rule_missing`. The default chart (`buchhaltung-standard.ts`) already contains 1400 and 4200. There is no dedicated interest payment voucher type. The export uses a linked voucher number or `FND-…`. The demo creates an interest payment on the date of every annual interest posting, as in the legacy backfill, and records outstanding interest in the trial balance as a receivable.

**Regulatory reporting.** Definition sources can select and load `zinszahlung` and `dividende`. The proceeds balance includes them, as metrics do. Built-in templates' “Proceeds and repayments …” fields still include only sale proceeds plus repayments. The templates also live in a migration, so new fields would require a data migration. To report interest paid and dividends separately, select the transaction types `zinszahlung` and `dividende` in a custom definition. “Interest booked” remains the interest posting (income after an interest run). Reported interest income uses that posting, and cash proceeds use the interest payment.

**Interest views.** `GET /beteiligungen/:id/zinsen?stichtag=&stand=` and `GET /fonds/:id/zinsen?stichtag=&stand=` require viewer at the fund (permission table and OpenAPI). Response: `{ beteiligungId | fondsId, stichtag, stand, instrumente: [...], summe }`. Per instrument: `beteiligungId, instrumentId, organisation { id, name }, bezeichnung, art, status, konditionen` (as of the date with number of versions, or `null`), `aufgelaufen` (due unposted periods plus current partial period, `null` without terms, for an inactive instrument or on calculation error), `gebucht`, `kapitalisiert`, `gezahlt`, `offen` (= booked excluding capitalised − paid), `naechsteFaelligkeit`, `perioden`, `fehler`, `fehlerCode`. Each period has `von, bis, faellig, betrag, gezahlt, offen, kapitalisiert, status, laufend, vorgangId` and status `aufgelaufen` (unposted), `gebucht` (capitalised), `offen` (booked and not fully paid) or `gezahlt`. Referenced payments settle their posting. Other payments settle the oldest outstanding postings in order. `summe` contains `aufgelaufen, gebucht, kapitalisiert, gezahlt, offen`. Fund view includes all its loan-like instruments. The fund role covers all its investments.

**Instrument and investment data.** `GET /beteiligungen/:id/instrumentdaten` and `GET /beteiligungen/:id` add `instrumente` at the as-of and knowledge dates, with `zusage, ausgezahlt, offeneZusage, offenesKapital, tilgungen, rueckfluesse, kapitalisiert, zinsen, wertberichtigungen, gezahlteZinsen, dividenden, offeneZinsen, buchwertabgang, buchwert, tranchen` (with `stand`) per instrument. `zustand` has `zinszahlungen` and `dividenden`. Investment transaction rows include `instrumentId, instrumentBezeichnung, trancheId, kapitalisiert, beglichenVorgangId`. Fund overview rows have `instrumente: [{ id, art, bezeichnung, status }]` (master data without as-of filtering), and `instrument` stays the type of the main instrument.

**Import.** A row in the “Investments” sheet is an instrument (`instrument` = type, with a new `bezeichnung` column). An investment is unique by fund and company. Additional rows with the same pair attach instruments to that investment, from the file or existing data. The file assigns increasing creation times in row order, so the first active row is the main instrument. “Transactions” and “Terms” sheets have an optional `instrument` column (type or name, takes precedence, findings `INSTRUMENT_UNBEKANNT` and `instrument_ambiguous`). The “Proceeds” control total stays sale proceeds.

Configurable tables (PDF portfolio and management list) still offer just the main “Instrument”. Adding a default column would change fund templates. ### Round transactions and bridge rounds

A company's round view shows the full history of fund transactions, with or without shares. Any transaction can be assigned to one of the company's financing rounds. Unassigned items appear under “No round assigned”. The “All” list shows all transactions chronologically with their rounds.

**Bridge round.** `finanzierungsrunde.art` (enum `runden_art`: default `eigenkapital`, or `bruecke`). A loan between priced rounds has its own bridge round without valuation or shares. Later conversion posts to the equity target round.

- Pre-money, post-money, price per share and total shares are empty only for bridges (`CHECK`: all four set for `eigenkapital`). A bridge holds a name, date and custom fields.
- A bridge starts `abgeschlossen` because there is nothing to validate or post. Closing and reopening return `round_type_bridge`. Share positions are rejected (`round_bridge_without_shares`), as are valuation fields with `art: bruecke`.
- `PATCH /finanzierungsrunden/:id` can change `art` to bridge for a draft without positions, equity instruments or conversions targeting the round (`round_in_use`). To switch to equity, give `preMoney` and `preisJeAnteil`. The round becomes a draft. A bridge can be deleted when nothing references it (instruments, conversions or transactions, otherwise `round_in_use`).
- A bridge never affects cap table, exit waterfall, investment metrics, `letzte_runde` valuation, report stage or the custom-field “latest round”. Those readers select only `art = 'eigenkapital'`.
- Loans, convertible loans, venture debt and shareholder loans may reference a bridge round. Equity and silent participation are rejected (`instrument_round_bridge`) on creation and when changing type or round. A conversion target must be `eigenkapital` (`round_not_equity`). The source loan can reference a bridge.

**Transaction-to-round assignment.** Transactions stay immutable (trigger `vorgang_kein_update_delete`). The editable mapping is `vorgang_runde` (`vorgang_id` primary key, required `runde_id`, `quelle` of `automatisch` or `manuell`, `geaendert_am`, `geaendert_von`). No row means unassigned. Each insertion, update or removal goes into the audit log (table `vorgang_runde`, record ID = transaction, state includes `fondsId`). `runde_buchung` still records what round closing posted and only supplies backfill data.

- **Default when posting** (`bucheVorgang` and all other paths: closing a round, conversion, sale and side postings, interest run, deal transfer, loan agreement and import). Use explicit `rundeId` first (must belong to the investment's company, otherwise `transaction_round_foreign`; `null` explicitly unassigns), then `instrument.runde_id`, then no round. Changing an instrument's round later affects only new postings and leaves prior automatic assignments intact.
- **Conversion.** All its postings (interest to cut-off, repayment, cash residual, commitment and target contribution) use the target round, including source loan postings.
- **Reversal** inherits the original's round, including reversal of a whole sale.
- **Manual change.** `PUT /vorgaenge/:id/runde` with `{ rundeId: string | null }`, requiring editor on the transaction's fund as for posting. The source becomes `manuell`. A round from another company returns `transaction_round_foreign`.
- **Round deletion** requires no transactions, instruments or conversions assigned (non-cascading foreign keys, as for `instrument.runde_id`).
- **Backfill** (migration `0064`). Assign from `runde_buchung`, then `wandlung.vorgaenge` (target round) and then instrument round. Reversals inherit the original and other transactions remain unassigned. Each step uses `ON CONFLICT DO NOTHING` in order so conversion postings do not end up on the loan's round.

**Reads.** `GET /organisationen/:id/rundentransaktionen` returns the company's visible rounds with `art`, their fund transactions in chronological order and unassigned transactions (`ohneRunde`). Only funds on which the caller has at least viewer level are included. Each transaction gives ID, value date, type, amount, fund, investment, instrument, tranche, shares (first unreversed commitment of an instrument with a fund position in that round, otherwise `null`), reversal flag and assignment source. The UI's “All” list combines those groups.

### Co-investor vehicles

An investor (organisation in CRM) holds a financing-round position through the fund or entity that actually invests. Fictional example: “Example Capital GmbH” with vehicles “Example Capital Seed Fund I” and “Example Capital Growth Fund III”. Internal funds keep their positions at `fonds_id`.

**Table `vehikel`.** Required `investor_id` (organisation), required `name` (unique per investor), `art` (enum `vehikel_art`: default `fonds`, `gesellschaft`, `spv`, `sonstige`), optional `auflagejahr` (1900 through 2100), `status` (enum `vehikel_status`: default `aktiv`, `in_liquidation`, `aufgeloest`), `standard` (at most one default per investor, partial index) and `erstellt_am`. Every vehicle belongs to exactly one investor.

**Round position.** `vehikel_id` replaces `rundenposition.organisation_id`. Exactly one of `fonds_id` and `vehikel_id` is set (`CHECK rundenposition_ein_investor`). The investor is always the vehicle's investor, with no second column that could disagree. Co-investor payments (`rundenposition_zahlung`) stay on the position.

- A round has at most one position per vehicle (`round_position_exists`). Two vehicles of one investor may hold positions in the same round.
- A position can move to another vehicle of the same investor (`PATCH …/positionen/:positionId` with `vehikelId`, different investor `vehicle_other_investor`, collision `round_position_exists`). After closing, the vehicle is the only editable field for this operation.
- Creating a position (round creation, add position, AI confirmation or import) takes `fondsId`, `vehikelId` or transitional `organisationId`. With `organisationId`, the API uses the investor's default vehicle and creates it if missing (investor name, type `fonds`, audit log entry). This preserves the import format.
- A new vehicle requires organisation type `investor` (`vehicle_not_investor`). The automatic default vehicle works for any organisation with positions or receiving one via `organisationId`, preserving its organisation type.
- A vehicle can be deleted only without positions (`vehicle_in_use`). The first vehicle becomes the default. “Set as default” moves the flag.
- **Merge organisations.** Source vehicles move to the target. For a duplicate name on the target, positions move to its existing vehicle and the source vehicle is removed. A default vehicle on the target clears the source's default flag. The preview counts positions of source vehicles.

**Reads.** Positions still return the investor organisation (`investor: { art: "organisation", id, name }`) and add `vehikel: { id, name } | null` (`null` for funds). This also applies to `halter` in the cap table and exit scenario. The cap table adds `inhaber`, with totals per fund, per investor across all their vehicles (including vehicle list and position count) and for common shares. Totals are shares, ownership and invested amount. The UI displays “Vehicle · Investor”. The waterfall still calculates per position, and investor grouping in the cap table is for display and totals. The waterfall also returns `inhaber` with the same grouping (funds, investors across vehicles, common shares and each employee equity pool) and sums of shares, invested, preference, participation, total, escrow and immediate proceeds, plus multiple. Group totals add up to row totals.

Vehicles are contact data in the contacts permissions area. Vehicle positions are round data and appear only when the person can see the round in the company's round list (role on a fund holding the company or in one of its closed rounds, all for global admins) with portfolio access.

**UI.** Organisations of type `investor` and organisations with vehicles get a Vehicles section in their table of contents. It has a vehicle table (name, type, vintage, status and positions), create and edit actions and positions per vehicle. Round and position dialogs pick co-investors by vehicle, search vehicle and investor names and show “Vehicle · Investor”. Organisations with no vehicle match appear below and are sent as `organisationId`, creating the default vehicle when saved. Users can still add an investor inline. A vehicle name creates and selects that vehicle immediately. With no name, the default is created when the position is saved. The cap table shows “Vehicle · Investor” and groups by investor. The exit scenario shows vehicle in the holder name. PDF reports still omit individual co-investors.

### Employee equity (ESOP/VSOP) and cap table views

Pools and grants belong to the company, like share classes. They are separate from funds and round positions.

- **Tables.** `mitarbeiterpool` has type `esop` or `vsop`, unique company label, and rule `wie_anteile` or `anteilig` (VSOP only). `pool_aenderung` holds date, nonzero size change, resolution, and optional round with basis `pre_money` or `post_money`. Supply both round and basis or neither. `mitarbeiterzuteilung` has category `gruender`, `fuehrung`, `mitarbeitende`, `beirat` or `sonstige`, optional label without names, count, strike price, grant date, vesting start, cliff and duration in months, acceleration as fraction, status `zugeteilt`, `gevestet`, `verfallen` or `ausgeuebt` with date and a `leaver_regel` note. `zuteilung_austritt` records one or more departures per grant with `art`, `austritt_am`, `anzahl`, `gevestet` and `rueckkaufpreis`.
- **Rules** (calculation engine `mitarbeiterbeteiligung.ts`, reference `referenz_mitarbeiterbeteiligung.py`). Vesting is linear in full months with cliff, rounded down. At exit add the accelerated part of unvested units. Size at as-of date = sum of changes. Outstanding = grants excluding forfeited and exercised units from their effective dates. Available = size − outstanding − exercised. The API requires size ≥ 0 (`pool_negative`) and grants ≤ size (`grant_exceeds_pool`) at each date. Forfeited units return to the available pool.
- **Leaver rules.** A *good leaver* departs without fault, for example on termination without cause, illness, retirement or often resignation after a minimum term. They usually retain vested units. A *bad leaver* departs for cause or breach (summary dismissal, violation of a non-compete or often early resignation). Vested units lapse or are repurchased at strike or nominal price. In both cases unvested units lapse and vesting stops at departure. Each departure (table `zuteilung_austritt`, any number per grant) has type label `good_leaver` or `bad_leaver`, date, rule for vested units (`bleiben`, `verfallen`, `rueckkauf`, default `bleiben` for good and `verfallen` for bad), units affected (default all remaining units on creation, with total departures capped at the grant count) and repurchase price (empty means strike price). In calculation engine `aufteilung`, each departure freezes vesting for those units, rounded down at its date and zero before cliff. Unvested units lapse and vested units follow the rule. The remaining units (count − departures through as-of date) continue vesting and can accelerate on exit. Retained leaver units do not accelerate. Lapsed and repurchased units return to the available pool. Fully diluted counts stay the same, but those units leave the waterfall. Repurchase amounts are informational. The API (`POST`, `PATCH`, `DELETE` under `…/zuteilungen/:zuteilungId/austritte`, returns the whole grant with `austritte` and `betroffen`) requires departure on or after grant, affected units ≤ count even when reducing or moving the grant, price only for repurchase and no departures on exercised grants. Every departure date counts for pool validation, including on deletion. Status `verfallen` remains for forfeiture of the whole grant. For partial departures, the UI shows the status of remaining units with the affected count out of the total.
- **Views.** Undiluted = issued shares (last round total plus ESOP options exercised after that round, as earlier exercises are already in the count). Fully diluted adds outstanding and available units for each ESOP and VSOP pool. Open conversions are included only with the switch below. Configure the default per installation (`KAPITAL_SICHT`, default `voll_verwaessert`). The cap table returns both ownership shares per row and the interface switches between them. Valuation scenarios derive the fund's share and latest-round enterprise value on the default basis and label it (`anteilBasis`).
- **Conversion parameters on the instrument.** Nullable convertible loan (`instrument`) fields: `wandlungsabschlag` (fraction from 0 to below 1 with at most six decimal places, percent in the UI), `bewertungsobergrenze` (amount greater than 0 in investment or fund currency, as `beteiligung.waehrung` in instrument data indicates), and `zinsen_wandeln` (yes, no or blank for unrecorded). Set through `POST /beteiligungen/:id/instrumente` and `PATCH /instrumente/:id` (`null` clears), with editor in portfolio. Other types return 409 `instrument_not_convertible_loan` and switching away from convertible loan clears the values. Instrument overview returns them per instrument. The UI has a conversion parameters group in Edit instrument (convertible only), a conversion group on the card and defaults in Conversion (discount, cap, convert interest). Shares before the round for the cap remain an input. Citations remain evidence and serve as a fallback. Contractually different principal and interest amounts belong to each conversion. See the contractual adjustments under [Phase 2 status](#phase-2-status-api-by-instrument).
- **Round positions of other internal funds.** The cap table shows name, share class, shares and round amount as for other shareholders. Carrying amount, own valuations and costs require read access on that fund. Transfers and exercises follow their own visibility rules.
- **Open conversions.** The fully diluted view offers “Include open conversions” (`GET /beteiligungen/:id/kapitaltabelle?offeneWandlungen=true`). It covers each convertible loan from a fund in the installation with principal at the as-of date, based on transactions through that date. A conversion whose cut-off or target round is on or before the date is excluded. Estimate in `schaetzeOffeneWandlung`: outstanding amount = outstanding principal (including capitalised interest) + unposted interest since the last posted period. Assume interest converts, while posted outstanding interest stays a receivable. Without terms, omit interest and show `ohne_zinsen`. Conversion price = min(valuation cap ÷ fully diluted shares before conversion, last round price × (1 − discount)). Without discount, use the round price itself. Round shares down. Discount, cap and convert-interest come from the instrument fields first, independently by field. Any missing discount or cap can fall back to investment citations (`wert_quelle`, `wandlungsabschlag`, `bewertungsobergrenze`) if the investment has exactly one open convertible loan and agreeing values. A blank convert-interest setting assumes yes (`zinsenWandelnAngenommen`). No excludes unposted interest. Return open instead of estimated (`status: "offen"`, `grund`) on `keine_parameter` (neither discount nor cap), `kein_referenzpreis` (no round), `parameter_mehrdeutig` or `ungueltige_parameter`. If only one of discount and cap is missing, estimate and name it in `fehlend`. Always return `offeneWandlungen`. With the switch, include estimated shares as `halter.art = "wandlung"` rows (unissued, group `wandlung`) and use `anteileMitWandlungen` as the fully diluted denominator. Each conversion estimates independently on the same basis. Include only loans from funds where the user sees portfolio. Other funds' loans and even their count are hidden. Citations require document visibility. The model excludes third-party convertible loans. Waterfalls, curves and scenarios omit estimates. The UI labels estimated rows with a tooltip and shows an Open conversions table with assumptions and reasons for unestimated open loans.
- **Waterfall.** Add one classless row per grant with units at exit date and strike price. It shares residual after preferences like common shares and receives max(0, amount per share − strike price) per unit. Strike price from in-the-money units stays with the other shares. The equation is shared by ESOP with exercise or cash settlement and VSOP residual payouts. Rule `anteilig` reduces all payouts including preferences by the same ratio to fund VSOP payouts. Available and unvested units do not participate. Breakpoint `im_geld` marks units coming into the money.
- **Rounds.** With a pool, price per share is fully diluted: (total shares + pool after round) × price = post-money. Include top-ups on this round's pre-money basis and exclude post-money top-ups. If only the undiluted check matches, return a `PREIS_UNVERWAESSERT` notice rather than an error. Without a pool the existing check applies. If `anteileGesamtNach` is missing, derive it on the fully diluted basis (post-money ÷ price − pool).
- **Option pool shuffle.** The New financing round dialog can top up a pool to target t (share of fully diluted shares after the round) on a pre- or post-money basis. `POST /organisationen/:id/finanzierungsrunden/pool-vorschlag` calculates a proposal without writing (`pool-shuffle.ts`, reference `referenz_pool_shuffle.py`). A = issued shares before the round (total from the last closed equity round through its date plus subsequent ESOP exercises, or input without a round), P = prior pool (outstanding + available at round date), V = volume (investor sum or input).
  - Pre-money: price = pre-money ÷ (A + P + X). Resolve the circular dependence of price on X and X on price with Q = k × A ÷ (1 − k), where k = t × post-money ÷ pre-money and Q = P + X is the pool after the round. Solvable only for k < 1 (otherwise `ziel_unerreichbar`).
  - Post-money: price = pre-money ÷ (A + P), X = (t × (A + P + N) − P) ÷ (1 − t), with N = floor(V ÷ price).
  - X is the smallest integer that brings the post-round pool to at least t, with new shares rounded down. If the pool already meets t, X = 0. Proposed price has four decimal places.
  - Effective pre-money = price × (A + P). On pre-money basis it is pre-money minus price × X. On post-money basis it equals pre-money.
  - Dialog metrics show new shares, pool before and after (fully diluted percentage), price and effective pre-money. User-overridden top-up and price feed the metrics. The proposal requires round read access because it discloses pool and shares.
  - Creation includes `poolAufstockung` (`basis`, `anzahl`, optional `poolId`, `neuerPool` with type and label, `beschluss`) in `POST …/finanzierungsrunden` and `…/vorschau`. The API creates a dated `pool_aenderung` tied to the round and its basis in the same transaction. Without `poolId` use the only pool, create one if none exists or require a choice if several exist (`pool_waehlen`). A pre-money top-up counts for validation and derived `anteileGesamtNach` in preview and creation. Post-money does not. Top-up requires editor with a legal basis on the company, as for adding a change. A fund entering only through this round can create the round but cannot top up. Draft deletion removes its top-ups if grants still fit (`grant_exceeds_pool` otherwise) and requires the same permission as adding a top-up. The top-up is effective from its date in the cap table and prior pool for a later round, even while the round is a draft. Target is at most 0.99 and prior shares at most 15 digits. A target with 1 − t < 0.01 (pre-money: 1 − k < 0.01) is unreachable. No migration.
  - **Top-up and draft.** Changing round date (`PATCH /finanzierungsrunden/:id`) moves linked pool changes dated on the previous round date. A change manually linked with a date of its own (for example a later resolution) stays put. Moving it needs top-up creation permissions, locks affected pools and validates their balance with the new date. On `grant_exceeds_pool` or `pool_negative` the round is unchanged. Switching a draft to a bridge is rejected while pool changes are assigned (`round_has_top_up`). Delete the draft and create a bridge instead. If a pool created by the draft would be left without changes and grants, deleting the draft deletes the pool in the same transaction. No migration.
  - **Individual changes.** `PATCH` and `DELETE /organisationen/:id/mitarbeiterpools/:poolId/aenderungen/:aenderungId` (editor in portfolio, as for creation). Lock the pool and validate the balance at each date with the edit or removal, including all departures (`pool_negative`, `grant_exceeds_pool`). Log `aendern` or `loeschen` for each `pool_aenderung`. Set round and basis together or both `null`. Editing or deleting a round-linked change requires draft status (`pool_change_round_fixed`, reopen first), as does assigning to a new round during edit. Creation may reference a closed round when recording historical data, so round validation uses its pool. Lock involved rounds with `FOR SHARE` before locking the pool, in the same order as round routes. Closing, reopening, converting or deleting the round waits for the write. A separate date is allowed and then does not follow round rescheduling. A pool's only change defines its size and cannot be deleted (`pool_last_change`). Bridge rounds cannot receive changes on creation, edit or with a new pool (`pool_change_bridge`), because bridges have no top-up. The UI's size history offers Edit (side panel form grid) and Delete (confirmation dialog). No migration.
- **Permissions.** The pool is aggregated cap table data without personal information. Visibility matches the company's rounds, requiring a fund with legal basis at the company or a position in one of its rounds. Creating and editing require editor, as for round creation. Validation, stored values and responses always calculate with the full pool. New round previews include it only when read access comes from already linked funds, excluding funds in the request body. Otherwise preview calculates without a pool.
- **Demo.** The company with the full investment chain has an ESOP pool after the follow-on round with three grants (management, staff and advisory board).

### SAFE, warrants and share transfers (issue 148)

- **SAFE** (`safe`) is not loan-like and has no terms, interest or manual repayments. Discount and cap work as for convertible loans (`wandlungsabschlag`, `bewertungsobergrenze`) without an interest conversion option. Investment uses commitment and disbursement. `POST /beteiligungen/:id/wandlung` converts it (calculation engine `wandlung` without interest terms, same postings, non-cash in journal). Open SAFEs appear in the fully diluted view like open convertible loans without interest. The cap uses pre-round shares, as with convertible loans. The model has no distinct post-money cap. A SAFE may be linked to a bridge round.
- **Warrants** (`optionsschein`) have count (`optionsschein_anzahl`, one share per warrant), exercise price per share in investment currency, issue date and expiry on the instrument. Any warrant purchase price is a normal commitment and disbursement. Exercise (`POST /instrumente/:id/exercises`, table `optionsschein_ausuebung`) posts count × exercise price as commitment and disbursement on the instrument (carrying amount, IRR, multiple and journal as for any disbursement). Exercised shares are the fund's issued shares in the instrument's class, common if empty. Exercise at or before the last round is already counted in its shares and reduces common shares. Outstanding unexpired warrants count as fully diluted and enter the waterfall with exercise price as strike (like options with rule `wie_anteile`, without class). Unexercised warrants lapse at expiry. Third-party warrants and convertible loans are outside the model.
  Reverse only the full exercise (`POST /instrumente/:id/exercises/:exerciseId/reverse`, field `reason`). Reverse commitment and disbursement, exclude the exercise (`storniert_am`) and reopen the warrants. A locked exercise period or a transfer drawing from the shares blocks reversal (409 `warrant_exercise_reversal_dependent` for a dependent transfer). Reversing individual transactions returns 409 `reversal_not_allowed`.
- **Share transfer** (table `anteilsuebertragung`, `GET`/`POST /organizations/:id/share-transfers`, English fields). The source is an issued cap table row on the date (round position, earlier transfer or common shares). The buyer is a fund in the installation or a vehicle. It issues no new shares. Transferred shares retain class and round and take their pro rata preference base rounded to cents. The price between shareholders leaves preference unchanged. Internal funds record disposal as a sale on the source instrument (share = transferred ÷ held shares) and acquisition as a new equity instrument with purchase-price commitment and disbursement. Backdated transfers must leave later transfers valid. Require editor on the company as for rounds (the buyer fund does not count) and on all participating internal funds.
  The source can also be a fund's exercised warrant row (`ausuebung:<id>`, column `quelle_ausuebung_id`). The sale applies to the warrant instrument. Dispose of carrying amount equal to acquisition cost of transferred shares (count × (exercise price + purchase price per warrant)). Purchase price per warrant is what remains attributable to the untransferred holding after deducting exercise amounts for held exercised shares. The instrument stays active while the holding contains warrants.
  Reverse only the whole transfer (`POST /organizations/:id/share-transfers/:transferId/reverse`, field `reason`). Reverse the selling fund's sale and the acquisition instrument's commitment and disbursement. The instrument then becomes written off and the investment remains. The transfer stays listed with `reversedAt`. Reversal is blocked by a locked period, a later transfer from the holding (409 `share_transfer_reversal_dependent`) or subsequent postings to the acquisition instrument (409 `share_transfer_reversal_instrument_used`). Creation permissions apply.
- **Carrying amount per instrument after a whole-investment sale** (issue 208). Allocate carrying amount disposal without an instrument pro rata by instrument carrying amounts immediately before sale (cents by largest remainder, engine `verteileBuchwertabgang`). Instrument disposals sum to the investment's disposal. A later instrument sale uses its reduced carrying amount.
- **Demo.** The company with the full chain has unexercised venture-debt warrants with no purchase price, a bridge SAFE after the follow-on round (commitment and disbursement, open conversion) and a common share transfer to a co-investor vehicle.

### Funds of funds: target fund holdings (issue 160)

A fund may hold interests in other funds (`zielfonds_beteiligung`). Each target fund has commitments, capital calls and distributions (`zielfonds_bewegung`, immutable with reversals for corrections) and as-of NAV reports with the holding NAV and/or share of the target fund (`zielfonds_meldung`, immutable, last recorded report for an as-of date wins). Amounts use the fund-of-funds currency.

- **Holding value** (`zielfondsWert`). If the target is in this installation and the share has been reported, use **look-through** (target NAV at as-of date × share). Otherwise use the **latest NAV report**, rolled forward with subsequent calls and distributions. Without a report use **cost** (calls minus distributions, floored at zero). Cycles such as A holding B and B holding A are excluded from look-through.
- **Target fund metrics.** Commitment, calls, unfunded commitment, distributions, value, DPI, TVPI and IRR (XIRR), each with provenance.
- **Fund NAV.** Target values enter as a separate “Target fund holdings” calculation step (portfolio value + target funds + bank + other assets − liabilities). The trial balance lists holdings as financial assets, whose carrying amounts are excluded as for other investments. Funds without targets calculate as before. New movements or reports and changes to the look-through target make fund-of-funds snapshots stale.
- **Double counting.** Cross-fund totals subtract target holdings when both funds are included. Allocation excludes those holdings because the target's investments are already present. See [Currencies](currency.md).
- **Permissions.** Fund-of-funds NAV includes look-through value in fund overview, dashboard, currency view, reports, valuation scenarios, Excel, LP portal and MCP. Everyone with read access on the fund of funds uses the same snapshot. Without portfolio read access on an internal target, its holding appears in a combined “Target funds” row with other hidden holdings. Name, identifiers, share held, movements, reports and calculation steps require that access. Linking and editing also require write access on the fund of funds.
- **Cycles and depth.** A link closing a cycle or creating a chain deeper than three levels is rejected (`target_fund_cycle`, `target_fund_too_deep`). Look-through resolves at most three levels and caches each target NAV within the request.
- **API.** `/fonds/{id}/target-funds` (list, create), `…/{targetFundId}` (details, update), `…/movements`, `…/movements/{movementId}/reverse`, `…/nav-reports`. UI: Fund → Target funds.
- **Demo.** An additional fund of funds (latest vintage, listed last) holds one target in the installation and two external targets. Existing funds and their numbers remain unchanged (`schreibeDemoDachfonds`).

The model excludes recallable distributions, target fund fees as a separate movement type and importing calls from an internal target's capital accounts. Movements are entered on the fund of funds.

### Portfolio dashboard (issue 147)

`/portfolio` shows all visible funds in home currency: deduplicated NAV, paid-in, distributions, TVPI, DPI and RVPI with calculation steps. Allocation groups by sector, country (registered country in regulatory data), stage (label of the last closed financing round through as-of date) and fund. Each group shows invested and fair value (calculation engine `allokation`). History shows NAV and portfolio value per fund and total at recent quarter ends. NAV is available only for dates with an applied trial balance. Missing figures remain missing. Without a knowledge date, history reads stored snapshots. As-of and knowledge dates live in the URL.

### Demo portfolio

The seed follows the model (`packages/db/src/demo/modell.ts`, consistency test `packages/db/src/__tests__/demo-modell.test.ts`). Equity (direct and silent participation) has one instrument per fund position with the round and share class. Loans, convertible loans, venture debt and shareholder loans have a dedicated bridge round, tranches (often conditional after the first, fulfilled before disbursement), interest postings and repayments. Convertible loans accrue interest on account only. Converted loans carry API postings (calculation engine, `wandlung` row, target round, `gewandelt` status). Each investor has one to three vehicles (first is default). Co-investor positions are distributed among their investor's vehicles without randomness. `schreibeDemoPortfolio` no longer writes data.

### Principal disposal on loan sales and standalone waivers

A new sale transfers each affected active loan instrument's principal outstanding on sale date multiplied by the fraction sold, rounded to the nearest cent with halves away from zero. A full sale disposes of the entire remainder. The `principal_disposal` transaction records the sale ID. From that date, interest accrues on the remaining principal. A full sale records accrued but unposted interest through that date as receivable. Pro rata impairment is disposed of in the same sale and has a separate posting export mapping (`impairment_disposal`). Preview distinguishes principal disposal from carrying amount disposal. Sale gain is net proceeds after costs minus pro rata carrying amount. Performance uses actual cash received. Historical sales keep their postings and period balances. The record continues to flag remaining principal.

A waiver is available for every active loan-like instrument. Preview uses agreement date, principal, interest and reason. A visible document can evidence the agreement. Principal waiver posts a non-cash repayment. Any outstanding impairment on that principal is released in proportion to principal waived. Example: With €1,000 outstanding principal and €200 impairment, waiving €250 uses €50 of the impairment. Remaining principal is €750, carrying amount €600 and loss €200.

An interest waiver first settles posted outstanding interest. Any excess reduces accrued interest for affected periods and their later posting or capitalisation. Capitalised interest belongs to principal. The journal and posting export use dedicated types for principal waiver, interest waiver and disposal to a buyer. Waivers create no cash flow for IRR or multiple. Changes to terms use the existing terms amendment workflow.

Sales and waivers can each be reversed as a whole. Reversal checks the period of the original transaction and dependent postings. Writes require the same fund role in portfolio as a repayment.
